# Daily edition reissue v1

An additive, service-authenticated operator operation: `POST /internal/readings/edition-reissue`. It reserves exactly one successor to one named published Daily edition, in the generation family derived from that edition's retained evidence. It closes backlog item R04 without changing the legacy operation.

## What it binds

- **Exact target.** The request names the edition by `reading_id`, `revision`, `local_date`, and `generation_family`. The Worker loads the owner's row and requires every coordinate to match. It then decrypts the stored edition and requires the envelope format (v3 or v5), its identity, and its evidence header to agree with the row's `assembly_mode`. A disagreement fails closed as `target_evidence_invalid`, and a misstated family is `family_mismatch`.
- **Family and reason.** `deterministic` editions are reissued by the V1 assembler and accept `chart_recalculated`, `consent_revoked`, `safety_correction`, and `defect_repair`; none of these reaches a model. `constrained_model` editions are reissued by a V2 command recorded as `manual_reissue` and accept only `safety_correction` and `defect_repair`. A consent revocation never authorizes a new model call. A chart correction withdraws the stale edition through `/internal/readings/invalidate` and fact repair. The schema encodes this matrix, and the Worker enforces it again.
- **Date scope.** Resolved in the reader's confirmed zone when the request is made. `deterministic` covers the current local day only, because its builder always resolves today. `constrained_model` covers the current local day or the next one, which the scheduler pre-generates. The successor is frozen for exactly the target's local date.
- **Authorization and consent.** The account must be active and hold its current account-processing grant. A constrained-model reissue additionally requires the Daily rollout to admit the internal entry point, a configured publisher, and a live `ai_synthesis` grant. The reservation batch re-asserts the exact published edition, the account-processing grant, and (for `constrained_model`) the exact `ai_synthesis` grant the successor froze. Execution still re-checks consent before any provider work.
- **Idempotency.** The identity is the target edition. `uq_daily_readings_successor` admits one successor per predecessor, so a retry of the same request answers `200 replayed` with that successor, including after it published, failed, or was replaced, and freezes nothing new. Replay compares the successor's generation-1 command, not its active one, so a later replacement does not change its identity. A request naming the same edition with a different family or reason is `409 reissue_conflict`, and so is a fact-repair successor. A deterministic command records no reservation reason, so a legacy `/reissue` successor with the same reason answers as this operation's replay. No `Idempotency-Key` header is read.
- **Kill switch.** While the Daily rollout does not admit internal reservations, every constrained-model request, replays included, answers `503 rollout_disabled` before any key is loaded or calculation is requested.

## What it does not do

It does not re-freeze a failed successor; `/internal/readings/replace` does that within `MAX_COMMAND_GENERATION`. It does not invalidate anything, and it does not change `/internal/readings/reissue`, whose V1 builder still ignores the target's family. Each successor job keeps the four-attempt limit, and constrained-model provider calls keep the configured daily call ceiling. The target stays published until the successor's own publication supersedes it in one guarded batch.

Fixtures cover the public shapes and the family/reason matrix. Runtime tests cover ownership, stale and mismatched targets, evidence derivation, consent and authorization changes, dates, replay and conflict, concurrency, publication, and ceilings. No migration is required.
